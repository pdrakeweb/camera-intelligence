# Camera Intelligence: System Review and Scoped Improvements

**Reviewed:** v0.6.1 (`64d1c94`), 2026-10-05
**Scope:** everything in the repo: `custom_components/camera_intelligence/*`, `README.md`, `hacs.json`, `manifest.json`. The external vision agent isn't in this repo, so it's covered only through its contract (the push payload).

---

## 1. Verdict

The architecture is sound and small (~550 LOC of Python). It's a push-only state sink with a pure normalizer (`normalize_payload`) between the HTTP boundary and the entities. Keeping inference outside HA is the right call, and naming each entity for the thing it tracks is a model that will extend cleanly to animals and people.

The weaknesses are about **trust boundaries and staleness**, not structure:

1. **The integration can't tell whether the agent is still running.** If the agent stops, every entity keeps its last state forever. A `home` vehicle stays `home` indefinitely, and automations keyed on presence keep acting on data that went stale hours ago. This is the highest-impact gap.
2. **The payload boundary isn't validated.** Five malformed shapes crash the handler with an HTTP 500. Four more are silently misparsed into wrong entity states. All nine were reproduced; see section 3.
3. **The docs are wrong about entity IDs, the YAML config, how the vehicle list works, and network exposure.** The YAML example in the README fails schema validation as written.
4. **There are no tests, no CI, and no tagged releases.** The normalizer is a pure function and would be cheap to cover.

Nothing here needs a rewrite. Section 4 groups the fixes into eight work packages, each about one PR.

---

## 2. Architecture snapshot

```
vision agent ──POST /api/camera_intelligence/update──► CameraIntelligenceUpdateView
  (bearer token)                                         │ normalize_payload()  (pure)
                                                         ▼
                                     hass.data[DOMAIN]["state"]   (in-memory only)
                                                         │ async_dispatcher_send(SIGNAL_UPDATE)
                          ┌──────────────────────────────┴──────────────────────────────┐
                          ▼                                                             ▼
        sensor.* (13 entities: 6 vehicles + 7 rollups)            binary_sensor.package_{porch,driveway}
        RestoreEntity: last HA state restored on boot             RestoreEntity
```

- **Contract:** the agent sends one complete snapshot per push, and every field is overwritten on each update. That's fine, but it means a partial payload resets the fields it leaves out.
- **Persistence:** the HA state machine is the only persistence (through `RestoreEntity`). The raw payload is lost on restart, so `GET /state` returns `{}` until the next push even though the entities show restored values.

## 3. Findings

Severity: **H** = wrong behavior users will hit; **M** = wrong under plausible conditions, or a maintainability or security gap; **L** = hygiene.
Confidence: **Verified** = reproduced or confirmed directly in code; **High** / **Med** = reasoned from HA internals without running HA.

## 4. Scoped improvements

Each work package is sized as one PR. Effort assumes one engineer who knows the HA dev environment: **S** < 0.5 day, **M** 1–2 days, **L** 3+ days.

### WP1: Payload boundary hardening (v0.6.2) — S, *do first*

**Fixes:** C2, C3, C4, C5, C6, C9, C10, C11

- Replace the hand-rolled shape checks with a voluptuous `PAYLOAD_SCHEMA` that coerces as well as validates:
  - `vehicles: {str: dict}`, `visitors: [dict]`, `driveway_vehicles: [str]` (a bare string is wrapped as `[s]` instead of split into characters)
  - `zones: {str: Coerce(int)}`, plus booleans through `cv.boolean`, which accepts `"false"`, `"off"` and `0`
- Return HTTP 400 with `vol.Invalid` humanized text, and log a warning that includes the agent's IP.
- **`count` and `zones`:** when only `zones` is sent, derive `count = sum(zones.values())`. When both are sent and they disagree, prefer `zones`. Decide whether `delivered` should be forced on when the zone sum is above zero; that's a question about the agent contract, so write the answer into the README.
- **Config schema:** `DOMAIN: vol.Any(None, vol.Schema({...}))`, and `dict(config[DOMAIN] or {})`.
- **Reserved keys:** reject the vehicle keys that collide with fixed entity keys.
  - Don't change existing unique IDs, because that would orphan registry entries.
  - If namespacing is wanted later, do it in WP5 with a migration in `async_migrate_entry`.
- **Binary sensor restore:** map only `on`/`off`, and leave anything else as `None`.
- **Sensor restore:** skip `unavailable`/`unknown`, and restore only the keys this entity itself writes (whitelist per class).
- **Acceptance:** each of the 9 probe cases from section 3.1 returns 400 or the corrected value, covered by unit tests (see WP2).

### WP2: Tests and CI — M, *alongside WP1*

**Fixes:** P10, D4

- `tests/test_normalize.py`: pure pytest on `normalize_payload`, with no HA dependency. It needs `http.py`'s HA imports split out, or the normalizer moved to a `payload.py` that imports nothing from HA. Cover the README example, each legacy shim, and the C2–C5 cases.
- `tests/test_init.py` with `pytest-homeassistant-custom-component`:
  - config flow, YAML import, and push → entity state
  - restore across restart
  - staleness, once WP3 lands
- GitHub Actions:
  - `home-assistant/actions/hassfest`
  - `hacs/action` (category `integration`)
  - `ruff check` / `ruff format --check`
  - `pytest`
- Release workflow: when a `v*` tag is pushed, check that it matches `manifest.json`'s `version` and create a GitHub release. This fills the badge and gives HACS real versions.
- **Acceptance:** CI is green on the PR, and the first tag `v0.6.2` produces a release.

### WP3: Agent liveness and staleness — M, *highest functional value*

**Fixes:** C1, plus the restart gap noted in section 2

- Stamp `received_at` (UTC) on every accepted push.
- New `binary_sensor.camera_intelligence_agent`, `device_class: connectivity`:
  - `on` while the last push is newer than `stale_after`, `off` otherwise
  - re-evaluated with `async_track_time_interval` every 30 s
  - attributes: `last_update` and `seconds_since_update`
- New option `stale_after` (default 10 min), plus a policy for stale data:
  - **`hold`** (default, today's behavior, now visible through the connectivity sensor)
  - **`unavailable`**: the presence/event entities report `available = False`
  - Trade-off: `unavailable` is safer for automations, but it breaks any `from: home` trigger whose author didn't handle `unavailable`. That's why it's opt-in.
- Persist the last normalized payload and `received_at` with `helpers.storage.Store` (debounced save, which costs little). This lets `GET /state` and staleness timing survive a restart, instead of a stale `home` coming back after reboot looking fresh.
- **Acceptance:** with the agent stopped, the connectivity sensor goes `off` within `stale_after + 30 s`. In `unavailable` mode the presence entities go unavailable, and they recover on the next push.

### WP4: Vehicle roster and options flow — M

**Fixes:** C7, C8, and the README drift in D1

- Delete `DEFAULT_VEHICLES`. A fresh install starts with no vehicles.
- **Auto-discovery:**
  - Keep the `async_add_entities` callback in runtime data.
  - On each push, add entities for vehicle keys not seen before, and persist them in the entry's options.
  - This is what the README already claims happens.
- **Options flow:**
  - list and remove vehicles, and set display names (`qx80` → "QX80", instead of the current `.title()`, which produces "Qx80")
  - set `stale_after` and the staleness policy (WP3)
- Removing a vehicle in options also removes its registry entry (`er.async_remove`).
- YAML import: when an entry exists, `async_update_entry` with the YAML `vehicles` instead of aborting. Alternatively, deprecate the YAML path and raise an `issue_registry` notice.
- **Migration:** existing installs have `data.vehicles` (YAML) or nothing (UI). Bump `VERSION` to 2 and copy the effective list (including the old default if that's what was in use) into `options`, so nobody's entities disappear.
- **Acceptance:** a fresh install sees new vehicles appear on their first push; existing installs keep the same entity IDs.

### WP5: HA modernization — M

**Fixes:** P1–P9, C12. These are best kept to one PR because they touch the same lines.

- `manifest.json`: add `"dependencies": ["http"]`, `"single_config_entry": true` and `"integration_type": "hub"`, and drop the manual single-instance check.
- Move from `hass.data` to `entry.runtime_data`. Keep the view-registered flag at module level, since views can't be unregistered.
- `_attr_has_entity_name = True` and one `DeviceInfo(identifiers={(DOMAIN, entry.entry_id)}, entry_type=DeviceEntryType.SERVICE)`.
  - Existing entity IDs are unchanged because the registry wins.
  - Friendly names become "Camera Intelligence Sportage" unless `_attr_name` stays as-is, which is fine with a device named "Camera Intelligence". Check the dashboards after this change.
- `SensorDeviceClass.ENUM` with `options` for vehicle, all-vehicles, unknown-vehicle, guest and package. `unknown` becomes `None`, since HA renders it as Unknown natively.
- `RestoreSensor` with `async_get_last_sensor_data()`, so values keep their types.
- `Visitors`: `state_class: measurement` for long-term stats. Decide whether a history graph of visitor counts is wanted; if not, skip it.
- `_unrecorded_attributes = frozenset({"last_seen", "details", "zones", "streak"})` on the relevant classes.
- `DrivewayVehicles`:
  - state = count (an int), attribute `vehicles` = the list
  - this resolves C12
  - **breaking change** for anything that templates on the comma-separated state; either ship it as a new entity or bump the minor version with a changelog note
- `diagnostics.py`: return the last payload plus `received_at` (redact visitor names if the diagnostics will be shared).
- Remove `sensor.async_setup_platform`.

### WP6: API access control — S

**Fixes:** S1, S2, D3

| Option | Pros | Cons |
|---|---|---|
| **A. Keep the bearer token, add `require_admin = True` on GET; on POST, enforce `is_local(ip_address(request.remote))`** (recommended) | Small change; the token stays the credential; GET stops leaking presence to non-admin users | Behind a reverse proxy this needs correct `trusted_proxies`, or every request appears local |
| B. Move POST to `webhook.async_register(..., local_only=True)` | Unregisters cleanly on unload; no token on the agent box | The webhook ID becomes the bearer secret (it travels in the URL and may be logged); losing HA auth is a step down |
| C. A dedicated non-admin HA user for the agent, checked by `user.id` in the view | Least privilege; revoking the agent doesn't affect anyone else | Setup friction; the user ID has to be stored in options |

Recommendation: **A**, plus document C as optional hardening in the README. Then fix the README's "local only" claim so it's true.

### WP7: Documentation truth-up — S, *ship with WP1*

**Fixes:** D1, D2, plus the README side of C6 and C7

- Entity table with the real IDs. Note that installs from before v0.x may have registry IDs that differ.
- Add the `binary_sensor` platform, both zone sensors, and (after WP3) the agent connectivity sensor.
- Rewrite the YAML section, or mark YAML deprecated.
- A **Payload contract** section: required vs optional keys, types, the "full snapshot, omitted keys reset" semantics, the precedence between `zones` and `count`, and a JSON Schema file (`docs/payload.schema.json`) the agent can validate against before it pushes.
- A `CHANGELOG.md`.

### WP8 (optional): Payload v2 and the generic "things" model — L, *design only for now*

The module docstrings expect animals and people to come next. The current payload has a dedicated key for each kind, so every new kind needs a normalizer branch, a sensor class and a README section. Proposal:

```json
{
  "schema": 2,
  "things": {
    "vehicle.sportage": {"kind": "vehicle", "status": "home", "last_seen": "...", "last_camera": "..."},
    "animal.dog":       {"kind": "animal",  "status": "home"}
  },
  "events": {"guest": {...}, "package": {...}},
  "visitors": [...]
}
```

- One generic `ThingPresenceSensor` class, with `kind` driving the icon and the `options`.
- The normalizer accepts both v1 and v2 for one minor version, then the v1 shims (P11) are deleted.
- Only worth doing once a second kind of thing is actually being built. Until then it's a speculative abstraction.

## 5. Sequencing

```
v0.6.2  WP1 + WP2 + WP7    hardening, tests, CI, docs (non-breaking)
v0.7.0  WP3 + WP6          liveness and access control (adds entities; opt-in behavior changes)
v0.8.0  WP4 + WP5          roster/options flow and modernization (config entry migration v1→v2;
                           DrivewayVehicles state change is breaking, so flag it in the changelog)
later   WP8                when the first non-vehicle kind is built
```

Do WP2 before WP4 and WP5. Those two touch entity identity and restore, which is the part most likely to break silently on real installs, and the tests are the safety net.

**Total:** about 6–9 engineer-days for WP1–WP7.
